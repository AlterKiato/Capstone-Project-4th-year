## Verified local foundation

- getActiveAIAccount requires session-derived positive safe ID, expected session role, and active user/current matching database role. Students, Panel and cross-role requests are denied. Strict Zod accepts only fixed report/topic IDs and rejects extra fields, prompts, histories, URLs and forged scope/eligibility.
- adult-eligibility.ts always denies with registry-unapproved. groq-provider.ts hardcodes enabled=false/available=false, with no environment activation, SDK, credentials, fetch or database/storage access. UI actions return canonical static/unsupported/unavailable text and never read AI aggregates or call a provider.
- Internal aggregate preparation independently authorizes and rechecks current role. Admin uses existing Phase 7 totals/publication eligibility in a read-only repeatable-read transaction. Adviser uses one aggregate SQL query constrained by current researchGroups.adviserId; historical versions and archived owned groups are included, not latest-paper backlog.
- DTOs expose only four Admin or three Adviser count bands. Counts 0-4 are withheld. Adviser guards require five distinct contributors AND papers in total, each released subset and complement, plus the combined residual. Admin publication uses approved/published/total complement checks. No identities, titles, abstracts, feedback, raw records, PDFs, paths, dates or signed URLs are projected to DTOs. All-withheld means null. Suppression is conservative, not formal anonymization.
- Internal local aggregation does **not** establish adult/provider eligibility. Ownership is scoped at query time; the later role recheck does not verify unchanged cohort ownership. No provider-output validator, live timeout, shared limiter, daily cache, scope invalidation or deployment egress enforcement exists. No private data currently leaves this boundary. Student guide and manual review workflows remain unchanged.

## Eligibility and deployment requirements (proposed, not implemented)

**Institutional registry:** Designate an independent authorized verifier; no requester self-approval. Bind a minimal server-only record to the existing account: adult eligibility result, verification provenance/verifier, verified/expiry times, policy version and revocation state. Do not store DOB or identity-document copies in the AI layer or export registry data. Approve a protected authoritative registry and change audit process; a static deployment file cannot promise immediate revocation without a governed redeploy/disable process. Proposed 90-day reapproval requires owner acceptance. Missing, expired, revoked, unavailable or mismatched entries deny AI. Check live eligibility before sending and returning any generated/cached response; invalidate on account/role/registry changes. Revocation cannot retract content already sent.

**Shared limits/cache:** No configured shared store is evidenced by package/config/source inspection. Vercel is a documented target, not a verified deployed project/plan/region. Recommend one approved managed Redis store for atomic reservations, leases and minimized daily snapshots; Lua execution supports atomic read/check/write. This is a feasibility recommendation, not deployed support or a free-tier guarantee. [Redis atomic scripting](https://redis.io/docs/latest/develop/programmability/eval-intro/), [Upstash REST support](https://upstash.com/docs/redis/features/restapi)

Keep proposed combined limits: 3 attempts/account/UTC day, 10/deployment/day across Admin/Adviser, 120-second account cooldown, one active request/account and deployment. Reserve all gates atomically; failures consume attempts, no retries, expiring leases with safe release. Enforce provider organization token limits too; byte size is not token accounting. Fail closed on store failure. Use one daily minimized snapshot (<=24h TTL), shared Admin scope and private Adviser scope, with policy/version keys and single-flight creation. Authorize every cache read. Validate private ownership/group-paper scope fingerprints; immediately invalidate on change and withhold until next day's snapshot instead of regenerating multiple cohorts. Cache no raw records; keep scope metadata private. Native page caching/process memory is not evidence of shared atomic enforcement.

**Outbound controls:** next.config.ts only configures Server Action upload size; no AI network policy is present. Vercel documents dynamic outbound IPs and Enterprise Secure Compute; static IPs are not destination restrictions. Actual deployment ability to enforce deny-by-default egress is unverified. [Vercel outbound IP guidance](https://vercel.com/kb/guide/how-to-allowlist-deployment-ip-address), [Secure Compute](https://vercel.com/docs/networking/secure-compute)

Future provider gateway must accept only server-built DTOs, fixed HTTPS api.groq.com chat-completions destination/model, reject redirects, have bounded request/response and 10-second timeout, and have no repository/storage/tools imports. Application checks alone are not a network firewall. Owner must approve a demonstrable egress policy on the selected runtime or isolated gateway; allow ordinary application DB/storage and approved registry/cache infrastructure separately. Do not claim Vercel WAF protects outbound traffic. Keep activation blocked where required network enforcement cannot be demonstrated.
