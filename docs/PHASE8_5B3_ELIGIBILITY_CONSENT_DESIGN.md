## Small UI and non-blocking behavior

Use a compact AI Eligibility dialog in existing User Management, not a new dashboard. Default visible state for every missing record is **Pending Verification**. Three choices: Pending Verification, Eligible, Not Eligible. Eligible means independently confirmed adulthood (18+ plus approved institution/provider requirements) and permitted institutional use; role or account activity proves neither. Unable to verify remains Pending, not a fabricated certification.

After a successful future authorized Admin/Adviser creation, open this dialog **after account creation commits**. Closing, skipping, denial or save failure must leave the account successfully created and pending; display separate account-success/eligibility-save results. Since creation UI is absent, the smallest first implementation attaches the same dialog after an existing role change to Admin/Adviser and provides an AI Eligibility row button for existing eligible-role accounts. A future creation flow can reuse it; adding that flow requires explicit owner scope approval. Public Student registration stays unchanged.

Only designated verifiers get certification controls. Eligible/Not Eligible require an initially unchecked confirmation: 'I independently verified this account against the institution-approved AI eligibility requirements.' Server requires literal confirmation=true for either certification. Pending is the default/no-decision state. Revocation is a separate explicit confirmed action, setting effective Not Eligible; reset for investigation sets Pending. Do not collect free-text reasons, DOB, evidence files or student data. Show the account reference and decision timestamp only to authorized management viewers; verifier identity stays in restricted audit access.

Own-account certification controls are absent; direct requests are denied. General Admin account-management authority is not verifier authority. Eligibility changes never deactivate an account, alter its role, change research/review data or hide normal reports. Pending/Not Eligible users retain reviewed static assistance. Student chatbot stays entirely static and has no AI consent prompt; Panel excluded.

## Designated-verifier governance and bootstrap

Recommended smallest authority model: designated **active Admin** accounts only, separately approved by an institutional officer; no new application role. A designation alone cannot certify: the verifier must also have a current independent Eligible decision and cannot certify/revoke/reset their own eligibility. Consent is unnecessary to administer eligibility because certification itself makes no provider request.

No ordinary Admin UI/API can grant verifier designation. A protected, separately authorized operator procedure provisions/revokes designations, tied to an institutional authorization reference; no client/JWT/verifier checkbox grants authority. Bootstrap requires an independent institutional officer to verify the initial verifier's adulthood/eligibility outside the app and authorize designation. Persist a bootstrap eligibility event with external authority reference and no self-verifier user ID, plus the designation. The requesting Admin cannot run or approve their own bootstrap. Prefer an independent officer and separate trusted deployment operator; who holds these duties needs owner approval.

This avoids requiring the first verifier to self-certify or a circular pair of unverified accounts. Ordinary certification requires a different designated, independently Eligible Admin. Replacing the last verifier uses the same external institutional procedure, never a fail-open emergency web endpoint. No system-generated birthdate or age assumption.

Revoking designation blocks future certification immediately; deactivation/non-Admin role/current Not Eligible also blocks it. Previously certified accounts do not depend recursively on their certifier's present state: ordinary staff changes do not silently erase valid history. For suspected compromised certification, revoke affected account decisions explicitly using the recorded issuer; institutional remediation policy must be approved. No automatic 90-day expiry. Reassessment is event-driven, with explicit institutional revocation, not permanent trust in JWT/cache.

## Minimal persistent model and constraints (proposed)

Recommend **three additive tables**, leaving users and research tables unchanged. Separating authority from eligibility prevents ordinary account edits from granting certification power; append-only decision/consent events preserve withdrawal/reacceptance history without another audit table.

| Table | Minimal fields and behavior |
|---|---|
| ai_verifier_designations | user_id PK/FK users.id; institutional_authorization_ref (bounded opaque reference, no documents); granted_at; revoked_at nullable. Provision/revoke only through controlled operator process. Existing row may be reauthorized with explicit operator audit retained externally. |
| ai_eligibility_events | id serial PK; user_id FK; decision Pending Verification/Eligible/Not Eligible; event_kind certification/reset/revocation/bootstrap; verifier_user_id nullable FK; institutional_authority_ref nullable; recorded_at; decision_role_id FK for role binding (required for certification/bootstrap, nullable for reset/revocation). Append per transition; latest event by id for account is authoritative. No row means Pending. Revocation is a timestamped event with decision Not Eligible; history remains. |
| ai_consent_events | id serial PK; user_id FK; terms_version bounded string; terms_digest bounded hash of immutable text; event_kind accepted/declined/withdrawn; recorded_at. Latest event for account and current version must be accepted. No record, decline or withdrawal denies provider use. |

Use timestamptz for new event times; server/DB supplies actor references and timestamps. Index eligibility (user_id,id) and consent (user_id,terms_version,id); latest ordering is deterministic under serialized account transitions. Restrict FK deletes (no cascade erasure of certification/consent history); normal account lifecycle already uses deactivation. Retention/erasure policy requires owner approval before production.

CHECK constraints: finite allowed decisions/actions; normal certification has non-null verifier different from target, no external issuer, and Eligible or Not Eligible; reset has Pending; revocation has Not Eligible; bootstrap has external authority reference and no user certifier. Reset/revocation require a different verifier as well. Consent accepted/declined/withdrawn is explicit, with nonempty bounded version/digest. Bootstrap is permitted only through operator authorization, **not** merely because a row passes CHECK. Cross-table active role/designation/eligibility checks belong in services/transactions, not presumed expressible as simple CHECKs. Effective eligibility must also match certified role; role changes require fresh certification and consent. No unique(user_id,terms_version) on consent events because withdrawal and reacceptance are valid transitions.

Serialize updates by locking the target users row; certification also reads/locks authority and verifier eligibility consistently, with deterministic lock ordering. Strict input includes expected last-event revision to reject stale dialogs and duplicate/replayed acceptance after withdrawal. Append decision and restricted audit atomically; the event itself is authoritative. Do not rely on current post-update activity-log calls for atomic certification evidence. Runtime UI actions cannot edit/delete past events or designation rows. Database operator remains a trusted administrative boundary.

Inspect generated FK/CHECK/index SQL and existing user PK/role FK types; update schema exports through existing patterns. No edits to historical migrations, roles, research tables, credential columns or existing constraints.

No grandfathering, bulk Eligible decisions or acceptance backfill. Missing rows fail closed as Pending/no consent for existing/new accounts; therefore a mass backfill is unnecessary. Provision the first verifier only with independently authorized bootstrap evidence after migration. Stage against isolated synthetic data first, then separately approve target application. Keep Groq hard-disabled throughout. If migration/registry is unavailable, only AI access falls back safely; account creation must not depend on an eligibility insert.

## First-use AI Terms and Consent

Before optional AI interpretation, an institutionally Eligible active Admin/Adviser may open an AI Terms & Consent dialog from the existing assistance entry. Provide full reviewed versioned text, initially unchecked acceptance, explicit 'Accept and continue' and 'Decline / use static guidance'. Closing is not acceptance. While Groq is disabled, show this status and static guidance; never suggest accepting enables the provider. Recommend defer first-use acceptance until reviewed terms are ready; optionally allow preview now without collecting acceptance.

Proposed text topics, **draft for institutional approval**:

> Optional AI assistance explains only approved coarsened system/workflow statistics. It does not grade research, make decisions or produce official Adviser feedback. If separately enabled, approved aggregate bands and fixed instructions are sent to Groq; research content, identities, eligibility records and your consent record are excluded. Outputs may be inaccurate; you remain responsible for human review. You may decline or withdraw without losing normal account, reporting, research or static-guide access. Withdrawal prevents future AI requests but cannot retract data already sent. See the approved provider privacy/retention notice and institution contact before accepting.

Do not promise zero retention, guaranteed anonymity or zero cost. Individual consent does not establish adulthood, authorize other people's research disclosure, replace institutional lawful-processing approval, or resolve Groq terms/deployment blockers.

Keep immutable reviewed terms versions/text/digests in a small server-controlled module/document archive; no terms database/admin editor needed. Client submits only known terms version and literal acceptance=true; server checks exact current version/digest and derives account identity. Reject extra keys/forged account/older-version acceptance; acceptance records are not JWT claims/localStorage. Withdrawal uses a fixed action, works even after eligibility is revoked, derives own account, and appends withdrawn for active accepted versions; can be idempotent. Account inactivity already stops AI; support institutional assistance for recording withdrawal by an inaccessible/deactivated user, with approved audit procedure.

Provide 'AI Terms / Withdraw consent' in the same assistance dialog for own status, not a separate dashboard. Withdrawal discards displayed/generated results and future delivery; new AI use requires another explicit acceptance. Material changes publish a new required version, immediately deny old-version consent and require renewed unchecked acceptance. Do not edit text under the same version; maintain audit copies. Who approves materiality/text/contact and retention must be designated. Role change or eligibility revocation/reset invalidates prior consent by appending withdrawal transactionally; reactivation must never silently grant AI access, and restored eligibility requires fresh explicit consent.

## Authorization ordering and isolation

Fixed request validation remains mandatory. For every future optional provider action: **verified active database account -> current allowed role -> institutional Eligible decision -> accepted current consent -> authorized ownership/consistent aggregation/privacy suppression -> atomic quotas -> isolated provider boundary**. Missing/denied/revoked/stale/unavailable data fails closed; generic fallback leaks no eligibility evidence to other users. Recheck the same account, role, eligibility revision, consent revision/version and Adviser scope immediately before dispatch and delivery, including cache hits. Clear output on failure/withdrawal/revocation; no positive entitlement cache/JWT authority. Revocation cannot recall a dispatched request; discard its response and document the residual race.

Disabled provider short-circuits to static guidance with zero provider traffic regardless of eligibility/consent/flags. Static topics never require provider consent and never consume quotas. Registry, consent, identifiers and guard counts remain in the trusted authorization layer; Groq receives only existing minimized aggregate DTOs. Preserve k=5 paper/contributor/complement/residual suppression, fixed IDs, no arbitrary prompts/filters/URLs, shared-limit/cache requirements and provider isolation. This design does not activate Groq or satisfy Vercel egress/shared infrastructure gates.
