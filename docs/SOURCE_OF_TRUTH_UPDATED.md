    overwriting prior versions

    enforcement
4.  Offer a published repository of approved research accessible to
    authenticated users
5.  Provide limited adult-only AI interpretation of authorized aggregate
    administrative/workflow statistics, and a non-AI Student system guide

## 7. Storage & Document Handling

### Supabase Storage

-   **Bucket:** `research-submissions` (private)
-   **Path pattern:** `research/{paperId}/{version}/{sanitizedFileName}`
-   **Format:** PDF only
-   **Maximum size:** 10 MiB (10,485,760 bytes)
-   **Access:** 300-second / five-minute default server-generated signed URLs; authorized Adviser review uses 1,800 seconds under P.2C.4

### Upload Flow

Phase 10.2C.2 supersedes the File-bearing submission transport. The active Student interface creates an authenticated, durable upload intent from validated metadata, uploads directly to its exact private `staging/submissions/<intent-id>/upload.pdf` capability, then requires an explicit Submit research action. Uploading alone creates no academic submission. The old File-bearing action is blocked.

Finalization accepts only the intent ID. The server rechecks current account, group membership and revision eligibility; verifies provider metadata, actual bounded PDF bytes, size, signature and encoding; persists a final-path/SHA-256 plan; writes those bytes without overwrite; and atomically inserts the existing submission record and completes the intent. Short per-paper transactions surround Storage I/O. Existing version uniqueness, review/history, publication and signed document access remain.

Intent lifetime is 15 minutes, with two live intents per Student, one per Student/paper and ten new intents per rolling hour including cancelled/failed issuances. Signed upload capabilities can outlive the intent: persist their trusted provider expiration before exposure; never assume single use or revocation. Browser credentials are limited to the necessary publishable key and exact staging capability, held in memory. Only the opaque intent locator may be retained in session storage.

Migration `0014_submission_upload_intents.sql` is **APPLIED and verified only on the approved local development/test database**, with all 15 ledger entries matching. Existing academic records/schema/public sequences were preserved; private backup and verified recovery evidence remain outside Git. The owner-approved development/test bucket metadata is private, `allowed_mime_types = ['application/pdf']`, `file_size_limit = 10485760`; only those two restrictions were changed. Policy catalog visibility is **NOT VERIFIED**, and no policy preservation claim follows from metadata. Live signed uploads, anonymous document denial, unrelated-path capability isolation, CORS and hosted acceptance remain unverified. Cleanup is operator-only, read-only dry-run, with a 25-intent batch and eligibility after the later intent/capability expiry plus ten minutes; destructive execution is deferred. See the latest Master Context for evidence and remaining gates.

### Submitted Document Access Flow

```text
Authenticated request
→ submission ID validation
→ active-account/database-role verification
→ Student membership or Adviser ownership authorization
→ persisted submission/file metadata verification
→ storage path bound to submission paper/version
→ server-side signed URL: 300-second default; 1,800-second fixed Adviser review purpose
```

Submitted-document access requires an authenticated Student/Adviser session, positive submission ID validation, current active-account/database-role verification, Student group membership or Adviser group ownership, persisted submission/file metadata verification, and a storage path bound to the submission paper/version. Admin and Panel are denied under the submitted-document rules. Only the persisted path is passed to the existing server-only signer in private bucket `research-submissions`: 300 seconds by default, or 1,800 seconds for the validated Adviser-only review purpose introduced in P.2C.4. No client-supplied paper, path, version, identity, role or expiration is trusted. Repository and publication lifetimes remain 300 seconds.

Missing/invalid metadata, unauthorized access, and storage/database failures return controlled results without sensitive details. No permanent/public storage URL or credentials are exposed. The DB retains the storage path, not signed URLs. Published-repository access is a separate existing flow governed by publication eligibility; its rules do not grant submitted-document access to Admin/Panel.

Already issued signed URLs may remain usable after authorization is revoked until provider expiry: normally 300 seconds, now up to 1,800 seconds for Adviser review. Local clearing and the 28-minute renewal threshold do not revoke capabilities or already loaded content. Legacy/nonconforming paths outside the established naming convention are intentionally rejected; do not weaken validation. Full submission/review regression evidence is service-level; browser acceptance specifically covered document access. These are known limitations, not blockers.

## 8. Important Architectural Decisions

1.  **Layered Architecture:** Maintain clear separation between
    pages/UI, actions, validation, services, repositories, and
    persistence.
2.  **Server-Side Authorization:** Authorization is enforced in
    server-side services; UI restrictions are not security boundaries.
3.  **Signed URLs:** Private research documents are accessed through
    temporary signed URLs rather than public storage URLs.
4.  **Version Preservation:** Research submission history is preserved
    and prior versions are not overwritten by later submissions.
5.  **Notification Failure Tolerance:** Notification failure does not
    block the primary operation.
6.  **Unique Version Constraint:** The database enforces unique
    submission versions per research paper.
7.  **Status Consistency:** Related submission and research statuses
    must remain consistent with the defined workflow.
8.  **Role-Based Navigation:** The interface may expose different
    navigation paths based on role, but authorization remains
    server-side.
9.  **PWA-First Delivery:** Web/PWA is the primary client experience
    across desktop and mobile. Separate native/mobile/desktop clients
    are deferred unless a later requirement justifies them.
10. **Shared Backend:** Future client experiences must use the same core
    backend, data model, authorization rules, and business services.
